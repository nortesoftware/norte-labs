Subject: qodercli runs an embedded binary that reads hardware identifiers and reports to an Alibaba endpoint at first start, undocumented, with an undocumented opt-out

I measured the 42 agents in the ACP registry on 2026-09-16, installing each one in a sandbox and starting it with an ACP `initialize` and `session/new`, under strace, with a decoy home directory and no credentials. The finding about qoder is the paragraph at https://github.com/nortesoftware/norte-labs/blob/b35a5609d27aa1c75af5238a5b952fe3c5f1f21a/measurements/agent-plugins/findings.md#L104-L110; the full record of that run is line 36 of results/cells-acp.ndjson in the same directory (https://github.com/nortesoftware/norte-labs/blob/b35a5609d27aa1c75af5238a5b952fe3c5f1f21a/measurements/agent-plugins/results/cells-acp.ndjson#L36), and the method is in the README there.

At its first start, before any sign-in and before any prompt, `@qoder-ai/qodercli@0.2.14` (the version the registry pins) wrote an x86-64 ELF of 652,488 bytes to disk and executed it. The binary is embedded as base64 in bundle/qodercli.js, at offset 10,165,558 of the 38 MB file, beside an aarch64 ELF, a Mach-O for arm64, a Windows executable and a 7.4 MB SecurityGuardSDK64.dll; the Windows executable is code-signed with your own certificate (BRIGHT ZENITH PRIVATE LIMITED), so this is your build, not a stray dependency. The JavaScript around it calls the module "umid" and the result a machineToken.

I ran the extracted binary on its own, with its endpoint names pointed at a local listener, under strace. It read /sys/class/dmi/id/bios_vendor, bios_version, bios_date, board_vendor, product_name and sys_vendor, tried /sys/class/net/wlan0/address six times, read /etc/mtab, /proc/meminfo and /proc/version, and tried to open /dev/sda, which was refused. Its strings also name `dmidecode -t baseboard | grep Serial`, hdparm and lshw for a disk serial, checks for vmware, virtualbox, kvm, xen and the hypervisor CPU flag, and the fields machineToken, machineType, machineCode, vmInfo and vmTypeCode; the dmidecode call did not run in my traces. It then sent `POST /repPc.json?e=1000&pn=runtime-info&os=8&sv=1.5.0&pv=NA&pt=1` with `Host: sg-pum.alibabachengdun.com`, HTTP/1.0 in the clear to port 443 (my listener was a plain socket and read the request), a user agent ending in "SG/1.0.0", and a 2.4 KB base64 body that decodes to 1.8 KB of high-entropy bytes I could not decode. So I can say what it read and where it sent; I cannot say what the payload contains. The binary carries six endpoints, umid.daily.alibaba.net, pre-umid.alibaba-inc.com, us-pum.alibabachengdun.com, sg-pum.alibabachengdun.com, pum.m.taobao.com and pum.m.alibaba.com, and a compiler string naming CProtector_PC at gitlab.alibaba-inc.com. In the original trace the CLI's process tree connected to sg-pum.alibabachengdun.com and to download.qoder.com in the same window, stat'ed every top-level entry of the home directory between 2,300 and 2,800 times (~/.aws, ~/.ssh, ~/.netrc, ~/.bash_history and the rest) without opening them, and opened ~/.env twice, a dotenv walk that starts at the workspace and reaches the home directory.

In the JavaScript, the token the binary returns is cached and attached to requests to Qoder's service as the headers Cosy-MachineToken and Cosy-MachineType. The only way to turn the module off is the environment variable QODER_DISABLE_UMID_REPORT set to 1, true, yes or on; the documentation's environment-variable reference lists thirteen QODER_ variables and not this one, and the module does not consult the documented privacy.usageStatisticsEnabled setting. The module first appears in 0.2.9 (published 2026-05-08); 0.2.8, a day earlier, does not contain it, and the 0.2.9 release notes do not mention it. It is still in 1.1.54, published 2026-09-16, where it also refreshes the token every hour, give or take five minutes, while a user is signed in, and refetches on account change.

The privacy policy (last updated May 12, 2026) says, under automatically collected information, that you collect "identifiers (including device identifiers, probabilistic identifiers, and other unique personal or online identifiers)". It does not say that the CLI reads BIOS, board and product identifiers and the network address, that an embedded binary does it before sign-in, that the report goes to endpoints outside qoder.com, or that there is an opt-out. This is not usage telemetry; it is device identification, and I could not find it declared anywhere a user of the CLI would read.

I ran this once per version, on linux-x86_64, in a bubblewrap sandbox and once unconfined on the host with the same result; I did not go further than the strings, the traces and the deobfuscated module, and I have not looked at the IDE.

I would ask for three things: that the collection be documented where the CLI is documented, with what is read and where it is sent; that the opt-out be documented, or the collection gated behind sign-in or consent; and that the ACP registry entry, which lists the CLI for Zed and JetBrains users, say what the agent does before authentication. I have sent the registry's maintainers a note with the same facts through their private reporting channel. The records that show this are already public at the links above, as part of a study of all 42 agents; I intend to publish a write-up of this finding on its own on or after 2026-12-16, ninety days from today, or earlier if you tell me it has been documented or removed. I can share the traces, the extracted binary and the deobfuscated module.
