Subject: Marketplace plugins whose hooks download and run code the reviewed repository does not contain

I measured the Cursor Marketplace on 2026-09-16: all 330 approved plugins from the catalogue endpoint, each fetched at the commit the catalogue pins, and for each one every hook it declares run once in a sandbox with a synthetic event on stdin, under strace, with a decoy home directory. The method and the per-plugin records are public at https://github.com/nortesoftware/norte-labs/tree/main/measurements/agent-plugins.

The marketplace security page says "Every plugin in the Cursor Marketplace is manually reviewed before it's listed. We work with a small group of trusted partners and review each plugin for security, data handling, and quality" and that "Plugins in the marketplace are not automatically updated from source code. We manually review every plugin update, so nothing gets into the marketplace without explicit approval." Under "What risk does installing a plugin carry?" it says "Plugins are lightweight by design. They're largely markdown files and supporting files for skills, such as templates and scripts. No binaries are shipped.", that plugins respect the MCP allowlist and blocklist, and that "since all plugins are open source, we recommend reviewing a plugin's source code before installing." The Publisher Terms describe the review as a review of "the Plugin's code", with source access on request. All of that is accurate about what is shipped: none of the 330 repositories contains an ELF, PE, Mach-O or WASM file. The risk answer stops at what is shipped, and so, as far as it is documented, does the review. What the shipped scripts do is outside both. 36 plugins declare hooks. Four of them, on the events I ran, fetched a binary that is not in the repository and executed it, or arranged to.

corridor's sessionStart pipes https://app.corridor.dev/cli/install.sh into sh when the CLI is absent. The version comes from app.corridor.dev/cli/VERSION at that moment; the script downloads the GitHub release, installs it into ~/.corridor/bin, appends a PATH block to the shell profile and runs it, and the hook then runs `corridor install --target ide-extension --provider cursor` on every session start. monk's SessionStart downloads monk-agent-linux-latest.tar.gz from get.monk.io, 65 MiB, into ~/.monk/bin, starts `monk-agent serve` on localhost and posts to us.i.posthog.com from the plugin's own script and from the downloaded binary; the file behind that URL changed within hours of my run, and the script re-checks the remote checksum on every session start and re-downloads when it differs. jfrog's beforeSubmitPrompt, with no matcher, runs `npx --yes @jfrog/agent-guard` against releases.jfrog.io before every prompt; the package is unpinned and its platform dependency is a 35 MB static ELF. revyl's beforeShellExecution, matched to commands containing "revyl", downloads a release from GitHub into ~/.revyl/bin and launches it; of the four it is the only one that pins what it fetches, by tag and sha256, in the repository. Two more plugins install and run packages from an index inside a hook: crowdstrike-falcon-fusion builds a Python venv from pypi.org at SessionStart, astronomer-data installs 35 packages with uv at stop.

None of this is hidden. Every script is in the repository the review looked at, and one of the four, corridor, is a vendor your hooks-partners post names. What the review does not bound is where the script goes next: three of the four fetch "latest", one of them through curl | sh with the version chosen by a server, so the code that runs on a developer's machine at session start can differ from the code that was reviewed, without an update to the plugin and without a re-review. Reading the source, as the page recommends, shows the curl | sh line; it does not show what the server behind it will send that day. The MCP allowlist the risk answer relies on does not apply to hooks. And the listing does not show it either: a plugin's page lists its hooks by event name only (corridor's reads "Hooks 1 sessionStart"), and corridor's README at the pinned commit is one line.

One more case, without any hook. Seven plugins declare an MCP server that read ~/.aws/credentials and ~/.aws/config at its first start, before any tool was called: aws-core and aws-data-analytics (aws/agent-toolkit-for-aws), sagemaker-ai, aws-amplify, amazon-location-service and aws-serverless (awslabs/agent-plugins), and opensearch-agent-skills. That is botocore's credential chain doing what it does, the upstream packages document it, and six of the seven say it in a README the review had: three in the plugin's own README, two only in the repository's README, one as an optional prerequisite. aws-core, the one the repository tells Cursor users to "start here" with, says it nowhere a user or reviewer reads before installing: its README describes "Authenticated access to any of the 300+ AWS services" without saying where the credentials come from, the repository README's credential sentence sits in the sections for other hosts, and the only statement is inside a skill body the model reads after install. None of the seven descriptions mentions credentials, and the plugin page renders the description, the skill descriptions and the server names, not the README. I am not saying these servers should not read the credentials. I am saying that for one of them nothing the review approved says they will.

Some limits of what I did. Hooks ran on a synthetic event, so a hook matched to a pattern ran here on a command that would not have matched it; I say above which ones are matched. I killed each hook at 20 s, so corridor's download did not finish and its execution is read from the script, not observed. I ran on linux-x86_64, once, on 2026-09-16, at the pinned commits, with a decoy credentials file in place; the seven READMEs and descriptions were read at those same commits. I am not saying any of these plugins is malicious; each does what its own README or upstream documentation says it does. I am saying that the risk answer describes what is shipped and the review, as documented, reads what is shipped, and that for four listed plugins the behaviour is decided outside both, and for one more what the server reads at start is declared nowhere a user or reviewer would look.

As far as I could find, this has not been reported. The closest published work is a static scan of Claude Code marketplaces and GitHub repositories (arXiv:2609.07360, September 2026) that lists "hooks that pipe a download into a shell" as an observed class in a handful of setups and does not cover the Cursor Marketplace or its review; monk's own tracker has an open report that its downloaded agent's checksum comes from the same origin as the file (monk-io/monk-plugin#392, filed for another editor); and two forum threads with staff replies describe the update flow (SHA-pinned, re-reviewed) without touching what a hook fetches at runtime.
