Subject: qoder entry: the pinned version runs an embedded hardware-fingerprint binary before authentication

I measured every agent in the registry at commit b8978f1 (2026-09-16), installing each and driving it through `initialize` and `session/new` under strace. My results agree with your daily probe on 33 of the 34 agents it reaches, so I trust the comparison. The full data is at https://github.com/nortesoftware/norte-labs/tree/main/measurements/agent-plugins.

One thing your probe cannot see, because it asks only whether the agent answers `initialize`. At first start, before any sign-in, `@qoder-ai/qodercli@0.2.14` (the version qoder/agent.json pins) writes an embedded x86-64 ELF to disk and runs it. The binary reads the DMI identifiers under /sys/class/dmi/id, the network interface address and memory and disk information, and posts an encrypted report to sg-pum.alibabachengdun.com over plain HTTP on port 443; the CLI attaches the returned token to its API requests as Cosy-MachineToken. The only opt-out is an undocumented environment variable, QODER_DISABLE_UMID_REPORT. The module is present from 0.2.9 to the current 1.1.54. I am reporting the same facts to Qoder directly (their privacy policy has a generic device-identifiers clause and nothing about this), with a publication date of 2026-12-16 for a write-up.

qoder is quarantined (the pin froze at 0.2.14 because initialize failed in 0.2.15 and 0.2.16), but quarantine keeps the entry listed and installable through Zed and JetBrains. I am not asking for it to be delisted. I am asking whether an entry should say what the agent does before authentication, since the registry's promise to users is about authentication, and whether this one should carry a note until Qoder documents it. I can share the trace and the extracted binary.
